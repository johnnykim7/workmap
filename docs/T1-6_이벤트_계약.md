# WorkMap 이벤트 계약 정의

> 설계 버전: 2.0 | 최종 수정: 2026-06-23 | 관련 CR: CR-006

> 단계: 1. Requirements | 모듈 간, 시스템 간 이벤트 규약
>
> 내부 모듈 간 이벤트와 외부 시스템 연동 이벤트를 모두 정의한다.
> **v0.4(Jira 기반) 전면 반영**: 업무 단위를 `Task` → `WorkItem`으로 교체. 단일 `work_item` 테이블(Epic/Story/Task/Bug/Sub-task)을 전제로 한다.
> **인터페이스 바인딩 원칙**: 소비/발행 주체는 시스템명이 아닌 **역할명**으로 기술한다(예: "Slack" 대신 "알림 채널").

## 발행 이벤트 (WorkMap → 내부 모듈 / 외부)

> Phase 1은 내부 모듈 간 이벤트(Spring `ApplicationEvent`)로 시작한다.
> 외부 발행(Slack/Mail/Webhook)은 Phase 3+에서 **어댑터**로 추가하되, 계약(토픽+스키마)은 지금 고정한다.
> **알림을 유발하는 이벤트는 본 트랜잭션과 분리하기 위해 `@TransactionalEventListener(AFTER_COMMIT)` 비동기로 처리한다.**

### WorkItemCreated (v1)
- **트리거 조건**: 업무 항목 생성 완료 시(WMP-WI-001, 만들기 모달/인라인 생성)
- **주요 포함 데이터**: workItemId, projectId, issueType(Epic/Story/Task/Bug/Sub-task), parentId(nullable), assigneeId(nullable), createdBy, createdAt
- **소비 주체**: 활동로그 기록자(WMP-WI-011), 알림 발행자(담당자 배정 시), 진행률 집계자(상위 Epic/Story 진행률 재집계 — parentId 있을 때)
- **관련 기능 ID**: WMP-WI-001
- **정합성 전략**: Phase 1 인프로세스(Outbox 불요). 외부 발행 전환 시 Outbox 적용.
- **멱등 키**: workItemId
- **실패 처리**: Phase 1 — 활동로그는 동일 트랜잭션. 알림은 AFTER_COMMIT 비동기. 외부 전환 시 DLQ.

### WorkItemAssigned (v1)
- **트리거 조건**: 담당자 지정/변경 시(WMP-WI-006)
- **주요 포함 데이터**: workItemId, assigneeId, previousAssigneeId(nullable), assignedBy, assignedAt
- **소비 주체**: 알림 발행자(신규 담당자에게 배정 알림), 활동로그 기록자
- **관련 기능 ID**: WMP-WI-006
- **멱등 키**: workItemId + assigneeId + assignedAt
- **실패 처리**: 알림 실패가 배정 실패로 전파되지 않도록 비동기(AFTER_COMMIT).

### WorkItemStatusChanged (v1)
- **트리거 조건**: 상태 전이 성공 시(WMP-WI-007, **FSM 화이트리스트 통과 후** — BIZ-010)
- **주요 포함 데이터**: workItemId, issueType, fromStatus, toStatus, changedBy, changedAt
- **소비 주체**: 활동로그 기록자(WMP-WI-011), 알림 발행자(담당자), 진행률 재집계자(상위 Epic/Story — WMP-WI-010), 회사홈 집계자(완료/막힘 카운트)
- **관련 기능 ID**: WMP-WI-007
- **멱등 키**: workItemId + changedAt
- **실패 처리**: 활동로그·진행률 재집계는 동일 트랜잭션. 알림은 AFTER_COMMIT 비동기.

### WorkItemBlocked (v1)
- **트리거 조건**: 공통상태가 BLOCKED로 전이될 때(차단 사유 입력 완료, BIZ-005)
- **주요 포함 데이터**: workItemId, issueType, blockReason, blockedBy, blockedAt, assigneeId(nullable), mentionedUserIds[](본문/댓글 멘션 대상, nullable)
- **소비 주체**: 알림 발행자(담당자 + 멘션 대상), 회사홈 막힘 집계자(WMP-HOME-002, "막힘 중심 대시보드" §9.2)
- **관련 기능 ID**: WMP-WI-007
- **멱등 키**: workItemId + blockedAt
- **실패 처리**: AFTER_COMMIT 비동기.

### WorkItemMentioned (v1)
- **트리거 조건**: 댓글에 @멘션 포함 시(WMP-WI-009)
- **주요 포함 데이터**: workItemId, commentId, authorId, mentionedUserIds[], mentionedAt
- **소비 주체**: 알림 발행자(멘션 대상자)
- **관련 기능 ID**: WMP-WI-009
- **멱등 키**: commentId
- **실패 처리**: AFTER_COMMIT 비동기.

### WorkItemLinked (v1)
- **트리거 조건**: 연결된 업무 항목(이슈 링크) 생성 시(WMP-WI-013). 양방향 자동(A blocks B → B blocked by A)(기획서 §13.1)
- **주요 포함 데이터**: sourceId, targetId, linkType(blocks/blocked_by/relates_to/duplicates), linkedBy, linkedAt
- **소비 주체**: 활동로그 기록자(양측 항목), 회사홈 집계자(blocks 링크는 막힘 신호 보조), 알림 발행자(대상 항목 담당자)
- **관련 기능 ID**: WMP-WI-013
- **정합성 전략**: 양방향 링크는 동일 트랜잭션에서 함께 생성(역방향 자동). 이벤트는 1회만 발행.
- **멱등 키**: sourceId + targetId + linkType
- **실패 처리**: AFTER_COMMIT 비동기. Phase 2 구현.

### SprintStarted (v1)
- **트리거 조건**: 스프린트 시작 시(WMP-AGL-003). 포함 항목 확정·기간 고정(기획서 §6.1)
- **주요 포함 데이터**: sprintId, projectId, committedItems[](workItemId 목록), startDate, endDate, startedBy
- **소비 주체**: 활동로그 기록자, 번다운 스냅샷 생성자(시작 시점 잔여 포인트 기준선), 알림 발행자(프로젝트 멤버)
- **관련 기능 ID**: WMP-AGL-003
- **정합성 전략**: 프로젝트당 ACTIVE 스프린트 1개 보장은 전이 가드에서 처리(이벤트는 성공 후 발행).
- **멱등 키**: sprintId + startDate
- **실패 처리**: AFTER_COMMIT 비동기.

### SprintCompleted (v1)
- **트리거 조건**: 스프린트 완료 시(WMP-AGL-004). 미완료 항목 다음 스프린트/백로그 이월(기획서 §6.1)
- **주요 포함 데이터**: sprintId, projectId, doneItems[], carriedOverItems[]{workItemId, carriedTo(sprintId|BACKLOG)}, completedAt, completedBy
- **소비 주체**: 번다운 스냅샷 생성자(완료 시점 스냅샷 — 번다운/벨로시티 기준), 활동로그 기록자, 알림 발행자(프로젝트 멤버)
- **관련 기능 ID**: WMP-AGL-004
- **멱등 키**: sprintId + completedAt
- **실패 처리**: 이월 처리는 동일 트랜잭션. 스냅샷·알림은 AFTER_COMMIT 비동기.

### WorkItemDueApproaching (v1)
- **트리거 조건**: 스케줄러가 마감 임박(기본 1일, POL-007) 항목 탐지 시
- **주요 포함 데이터**: workItemId, issueType, dueDate, assigneeId, daysLeft
- **소비 주체**: 알림 발행자(담당자)
- **관련 기능 ID**: WMP-NOTI-002
- **멱등 키**: workItemId + dueDate (하루 1회)
- **실패 처리**: 스케줄러 재시도. Phase 2.

### WorkItemOverdue (v1)
- **트리거 조건**: 스케줄러/조회 시점에 지연(POL-002: due_date < today AND status ∉ {완료,취소}) 판정된 항목
- **주요 포함 데이터**: workItemId, issueType, dueDate, assigneeId(nullable), overdueDays
- **소비 주체**: 알림 발행자(담당자), 회사홈 지연 집계자(WMP-HOME-002)
- **관련 기능 ID**: WMP-HOME-002
- **멱등 키**: workItemId + dueDate (하루 1회)
- **실패 처리**: 스케줄러 재시도.

### MeasureUpdated (v1)
- **트리거 조건**: 목표·실적 측정의 현재값(currentValue) 변경 시(WMP-WI-016, 측정 추상화 — 기획서 §8.5)
- **주요 포함 데이터**: workItemId, measureUnitId, targetValue, currentValue, previousValue(nullable), valueType(NUMBER/BOOLEAN/SELECT), updatedBy, updatedAt
- **소비 주체**: 진행률 재계산자(progress = 현재÷목표(정량) 또는 상태 기반(정성)), 회사홈/보고 집계자(목표 달성률), 활동로그 기록자
- **관련 기능 ID**: WMP-WI-016
- **정합성 전략**: progress 재계산은 동일 트랜잭션(파생값 정합). 외부 발행 불요(내부 집계용).
- **멱등 키**: workItemId + updatedAt
- **실패 처리**: 진행률 재계산 실패 시 트랜잭션 롤백(파생값 정합 우선).

### ApprovalRequested (v1)
- **트리거 조건**: work_item이 승인 게이트 상태(`workflow_status.is_approval=true`)에 진입해 승인 행(PENDING)이 생성될 때(WMP-OPS-006, BIZ-110)
- **주요 포함 데이터**: workItemId, approvalId, statusId, approverId(nullable), approverRole(nullable), requestedBy, requestedAt
- **소비 주체**: 알림 발행자(승인자 — 역할 또는 지정 사용자), 활동로그 기록자
- **관련 기능 ID**: WMP-OPS-005, WMP-OPS-006
- **멱등 키**: approvalId
- **실패 처리**: 알림은 AFTER_COMMIT 비동기. 승인 행 생성은 게이트 진입 트랜잭션과 동일.

### ApprovalDecided (v1)
- **트리거 조건**: 승인자가 승인/거부를 처리할 때(WMP-OPS-006, BIZ-111). 다수 승인이면 전원 APPROVED 시 최종 APPROVED 발행
- **주요 포함 데이터**: approvalId, workItemId, decision(APPROVED/REJECTED), decidedBy, comment(nullable), decidedAt
- **소비 주체**: 알림 발행자(요청자), work_item 상태 전이자(APPROVED 시 다음 상태 진행 / REJECTED 시 반려 — POL-011), 활동로그 기록자
- **관련 기능 ID**: WMP-OPS-006
- **멱등 키**: approvalId + decidedBy + decidedAt
- **실패 처리**: 상태 전이(전진/반려)는 동일 트랜잭션(승인 결과와 work_item 상태 정합). 알림은 AFTER_COMMIT 비동기.

### UserInvited (v1) — CR-027
- **트리거 조건**: 관리자가 사용자를 초대할 때(WMP-AUTH-004). `invitations` PENDING 레코드 생성 직후.
- **주요 포함 데이터**: invitationId, email, role, departmentId(nullable), invitedBy, expiresAt
- **소비 주체**: 활동로그/감사 기록자. (인증번호 이메일 발송 자체는 이벤트가 아니라 WMP-AUTH-009 동기 호출로 처리 — 발송 실패가 초대 트랜잭션을 막지 않도록 best-effort.)
- **관련 기능 ID**: WMP-AUTH-004
- **멱등 키**: invitationId
- **실패 처리**: 활동로그는 AFTER_COMMIT 비동기. 인증번호 평문은 페이로드에 절대 포함하지 않는다.

### UserJoined (v1) — CR-027
- **트리거 조건**: 초대 수락(인증번호 검증 + 비밀번호 설정)으로 user 계정이 생성될 때(WMP-AUTH-006).
- **주요 포함 데이터**: userId, email, role, departmentId(nullable), invitationId, joinedAt
- **소비 주체**: 활동로그/감사 기록자. (WS 자동 합류 등 후속 연동은 Phase 후속.)
- **관련 기능 ID**: WMP-AUTH-006
- **멱등 키**: userId
- **실패 처리**: user 생성·초대 ACCEPTED 처리는 동일 트랜잭션. 활동로그는 AFTER_COMMIT 비동기.

### PasswordChanged (v1) — CR-027
- **트리거 조건**: 비밀번호 분실 재설정(WMP-AUTH-007) 또는 로그인 상태 변경(WMP-AUTH-008)으로 `password_hash`가 갱신될 때.
- **주요 포함 데이터**: userId, source(RESET/CHANGE), changedAt
- **소비 주체**: 보안 감사 로그 기록자. (선택: 활성 Refresh 토큰 폐기 연동 — Phase 후속, 현재 Phase1은 무상태 토큰이라 미적용.)
- **관련 기능 ID**: WMP-AUTH-007, WMP-AUTH-008
- **멱등 키**: userId + changedAt
- **실패 처리**: 비밀번호 갱신은 동일 트랜잭션. 감사 로그는 AFTER_COMMIT 비동기. 비밀번호·인증번호 평문은 페이로드 비포함.

## 수신 이벤트 (외부 → WorkMap)

> Phase 3+ 연동 후보. 계약만 선정의하여 어댑터 추가로 연동 가능하게 한다(외부 연동 개방성).
> 외부 수신은 **멱등 키로 중복 차단**(bp-common-lib `idempotency` 활용)하고, 처리 실패는 **DLQ**로 격리한다.

### FormSubmitted (v1)
- **트리거 조건**: 양식 빌더(WMP-ADM-005) 제출 시. 제출 → 연결된 업무 유형의 `work_item` 자동 생성(기획서 §13.5a)
- **주요 포함 데이터**: submissionId, formId, issueType(양식에 연결된 유형), projectId, fieldValues{}(양식 필드 → work_item 필드 매핑), submittedBy(nullable, 외부 게스트 허용), submittedAt
- **발행 주체**: 양식 제출 채널(역할명: "양식 접수 창구" — 내부 사용자/외부 게스트 모두) → 업무 항목 모듈
- **관련 기능 ID**: WMP-ADM-005 (Phase 3+)
- **정합성 전략**: 멱등 수신(submissionId 기준 중복 차단). 생성된 work_item은 WorkItemCreated를 재발행.
- **멱등 키**: submissionId
- **실패 처리**: 필드 매핑/검증 실패 시 DLQ 격리 후 재처리.

### ExternalIssueRaised (v1)
- **트리거 조건**: 외부 이슈 소스(코드저장소/이슈트래커 등)에서 이슈 발생. 현장 이슈 → 개발 백로그 전환(WMP-OPS-003)의 외부 유입 경로(기획서 §13.4)
- **주요 포함 데이터**: source, externalId, title, severity, raisedAt, mappingHint{projectId, issueType, parentId(nullable)}
- **발행 주체**: 외부 이슈 시스템(역할명: "이슈 소스") → 업무 항목 모듈
- **관련 기능 ID**: WMP-OPS-003 (Phase 3+)
- **정합성 전략**: 멱등 수신(source + externalId 기준 중복 차단). Outbox는 발행측 책임. 생성된 work_item은 원본↔신규 링크(WorkItemLinked) 유지.
- **멱등 키**: source + externalId
- **실패 처리**: DLQ 격리 후 재처리.

## 작성 규칙

1. 이벤트명은 PascalCase 과거형(WorkItemCreated, WorkItemStatusChanged, SprintStarted).
2. 업무 단위는 **WorkItem**으로 통일(v0.4). `Task`는 issue_type의 한 값일 뿐 이벤트명에 쓰지 않는다.
3. 소비/발행 주체는 **역할명**으로 기술(인터페이스 바인딩 원칙). "Slack" 대신 "알림 채널".
4. Phase 1은 Spring `ApplicationEvent` 인프로세스. 외부 전환 시 토픽·스키마 유지 + Outbox/DLQ 적용.
5. 외부 연동 이벤트(수신)는 멱등 키로 중복 차단(bp-common-lib `idempotency` 활용).
6. 알림을 유발하는 이벤트는 `@TransactionalEventListener(AFTER_COMMIT)` 비동기로 발행하여 본 트랜잭션과 분리한다.
7. 파생값(진행률 등) 재계산은 정합 우선 — 동일 트랜잭션에서 처리.

## 설계 철학 점검

- **인터페이스 바인딩**: 모든 발행 이벤트는 특정 수신자에 결합하지 않는다. 알림/활동로그/진행률 집계/회사홈/번다운 모듈은 계약(이벤트명 + 페이로드)만 보고 처리한다. 새 소비자(예: 외부 알림 채널)는 리스너 추가만으로 붙는다.
- **외부 개방성**: ExternalIssueRaised·FormSubmitted는 GitHub/Jira/자체 양식 어느 소스든 동일 스키마면 어댑터 추가만으로 연동된다. 코어(work_item 생성 로직) 변경 불요.
- **분산 정합성**:
  - **Phase 1(인프로세스)**: 단일 트랜잭션이 정합을 보장. 활동로그·진행률 재집계는 동일 트랜잭션, 알림은 AFTER_COMMIT 비동기로 분리.
  - **외부 전환 시(Phase 3+)**: **Outbox**(발행 정합성) + **멱등 수신**(중복 차단) + **DLQ**(실패 격리)를 기본 적용한다. 토픽·스키마는 본 문서에서 이미 고정했으므로 코어 재설계 없이 어댑터만 추가한다.
