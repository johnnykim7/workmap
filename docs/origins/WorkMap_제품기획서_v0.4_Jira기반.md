## 1. 프로젝트 개요

### 1.1 한 줄 정의

당사 내부의 개발·운영·고객사 대응·반복업무·경영공통 업무를 **Jira 방식 애자일 구조(Epic/Story/Task/Bug)** 로 관리하고, Backlog·Sprint·Board·Timeline·Report·회사홈으로 연결해 업무 누락과 지연을 줄이는 내부 업무운영 시스템.

### 1.2 목적

ClickUp/Jira 같은 상용 SaaS를 판매용으로 다시 만드는 것이 아니다.
당사 내부에서 흩어진 업무를 한곳에 모으고, 대표·관리자·실무자가 같은 기준으로 상태를 확인하며, **지연·차단·정체·담당자 부하·막힘**을 빠르게 발견하는 내부 운영 시스템 구축이 목적.

### 1.3 기본 방향

WorkMap은 **Jira를 핵심 벤치마킹 대상**으로 삼되, 그대로 복제하지 않고 **내부 물류센터 개발/운영 업무에 맞게 재해석**한다.

```text
업무를 Epic/Story/Task/Bug로 등록·구조화한다.
→ Backlog에 쌓고 Sprint로 끌어올려 계획한다.
→ Board에서 상태를 옮기며 실행한다.
→ Timeline/Release로 일정·배포를 본다.
→ 막힘·지연·리스크를 자동 감지한다.
→ 회사 홈(막힘 중심 대시보드)에서 전체를 본다.
```

## 2. 도입 배경과 문제 정의 (v0.3 계승)

- 업무가 메신저·이메일·구두·엑셀로 흩어져 누락·중복·지연 발생
- 대표/관리자가 실시간 현황을 모름 → 보고에 시간 낭비
- 무엇이 **막혀 있는지(blocked)** 가 안 보임 → 작은 조직일수록 치명적
- 개발 완료와 **현장 운영 반영**이 분리 추적되지 않음

## 3. 최상위 구조 (확정)

```text
워크스페이스
└ 프로젝트
   └ 업무 항목
      ├ Epic
      ├ Story
      ├ Task
      ├ Bug
      └ Sub-task
```

- **"스페이스 = 프로젝트"로 통일.** 별도 스페이스 계층을 두지 않는다.
  - 근거: Jira의 실질 단위는 프로젝트(보드·백로그·스프린트·릴리스가 전부 프로젝트 종속). 우리 규모는 프로젝트 1단계로 충분.
- 전체 관리 대상을 **"업무 항목"** 이라 부른다(Jira의 Issue/Work Item에 해당, 사용자 혼란 방지).
- 화면 표기 용어는 **"프로젝트"** (추후 "업무"/"업무공간" 등으로 변경 가능).

### 3.1 업무 항목 계층 depth

| depth | 유형 |
|-------|------|
| 0 | Epic |
| 1 | Story · Task · Bug (형제, 같은 depth) |
| 2 | Sub-task (Story/Task/Bug 누구의 자식도 가능) |

### 3.2 에픽 정의 (Atlassian 공식 기준, 확정)

> 출처: Atlassian 공식 — https://support.atlassian.com/jira-software-cloud/docs/what-is-an-epic (2026-06-23 확인)

- 에픽 = "큰 작업을 담는 기본 작업 유형. **본질적으로 여러 작은 스토리로 분해되는 큰 사용자 스토리**"("a large user story that can be broken down into a number of smaller stories").
- 계층은 **부모-자식 관계**로 표현 — 공식 문서도 딱딱한 계층표 대신 `parent` 필드로 에픽의 하위를 묶음. (우리 epicId/parentId와 일치)
- **에픽은 거의 항상 여러 스프린트에 걸쳐 전달됨**("almost always delivered over a set of sprints"). → 에픽 자체는 스프린트에 담지 않고, **하위 스토리/작업이 여러 스프린트에 나눠 담긴다**(§6과 정합).
- **에픽의 스코프 변경은 애자일의 자연스러운 일부** — 에픽은 고정이 아니라 유동적.
- **"기능(Feature)" 계층은 Jira 표준 아님** — 일부 변형/플랜에만 존재. 우리는 **4계층(Epic > Story/Task/Bug > Sub-task) 유지**, 기능·Initiative 등 상위/중간 계층 미도입.
- **드롭다운(만들기/양식)에 에픽이 나오는 것 = 정상**: "계층상 에픽이 위"인 것과 "만들 항목으로 에픽을 고를 수 있는 것"은 별개. 에픽도 누군가 생성해야 하므로 선택지에 포함됨.

| 개념 | 설명 | 예 |
|------|------|----|

## 5. Story vs Task (확정)

| | Story | Task |
|---|-------|------|
| 관점 | 사용자/현장 가치 | 가치를 만드는 작업 |
| 완료 기준 | 인수조건(그 행동을 할 수 있음) | 작업물 완성 |
| 스토리포인트 | 보통 매김 | 잘 안 매김 |

- 보통 Story 1 : Task 다수. **강제하지 않음.**

## 6. 백로그 / 스프린트 (확정 — Jira 백로그 화면 그대로)

- 둘은 **같은 구조**(같은 업무 항목). Jira 백로그 화면 안에 스프린트 영역 + 백로그 영역 공존.
- 차이는 "실행 여부"가 아니라 **"계획 단위"**:
  - 백로그 = 아직 이번 주기에 안 담음
  - 스프린트 = 이번 주기에 하기로 담음
- 실행 상태(TODO/진행중/완료)는 별도 축으로 항목이 가짐.
- Board(`/board`)는 현재 스프린트만 칸반(실행용), Backlog 화면은 계획용.

### 6.1 백로그 화면 구성 (Jira 실제 UI 기준, 확정)

> 무조건 Jira 방식(2026-06-23, 실제 스크린샷 기준).

```
[백로그 검색] [담당자] [필터]                          [차트][설정][⋯]
─────────────────────────────────────────────────────────────────
▾ 스프린트 1   22 6월–29 6월 (1개 항목)   [0][0][0]   [스프린트 완료] ⋯   ← 진행 중
   (스프린트 목표: AI검수 시스템 구축)
   ▣ ZGOH-1  AI 검수 시스템 구축          [할일▾]      [-][=][담당]
   + 만들기
─────────────────────────────────────────────────────────────────
▾ 스프린트 2   29 6월–6 7월 (0개 항목)    [0][0][0]   [스프린트 시작]⋯   ← 미시작(회색)
   "업무 항목을 끌어 놓거나 바닥글을 끌어 계획하세요"
   + 만들기
─────────────────────────────────────────────────────────────  추정치 0/0
▾ Backlog   (0개 항목)                    [0][0][0]   [스프린트 만들기]
   "백로그가 비어 있습니다"
   + 만들기
```

- **다중 스프린트**: 현재 스프린트 + **예정 스프린트 여러 개**를 백로그 화면에 줄지어 둔다. (현재 1개만 아님)
- **스프린트 헤더**: 이름 · 기간 · 항목 수 · **상태별 카운트(To Do/진행/완료)** · **추정치 합** · 접기.
- **액션 버튼**: 진행 중 스프린트 → `[스프린트 완료]`, 미시작 → `[스프린트 시작]`(앞 스프린트 진행 중이면 회색), 백로그 → `[스프린트 만들기]`. (§13.2 P1)
- **드래그앤드롭**: 항목을 스프린트↔백로그로, 스프린트 바닥글을 끌어 범위 조정.
- **인라인 생성**: 각 영역 `+ 만들기` 로 모달 없이 행 추가.
- **행 인라인 편집**: 상태(할일▾)·우선순위·담당자를 행에서 바로 변경.
- **스프린트 완료 시**: 미완료 항목 → 다음 스프린트 또는 백로그로 이월(선택).

## 7. 프로젝트 유형과 화면 구성

프로젝트 생성 시 유형을 고르면 기본 탭(뷰) 조합이 프리셋으로 켜진다. **유형은 고정이 아니라 기능 조합의 출발점**이며, 탭은 켜고 끌 수 있다(기능 카탈로그 조합).

### 7.1 개발형
`Backlog · Sprint · Scrum Board · Timeline · Release · Report · 문서`
예: WMS 1.0 구축, OMS 2.0 개발, AI 판정 시스템

### 7.2 운영형
`Kanban Board · List · Calendar · Form · Approval · 첨부 · 문서 · Report`
예: 반품 운영 안정화, 쇼핑몰 운영, 현장 개선 요청

### 7.3 계획형
`Goal · Plan · Timeline · Dependency · Risk · Decision · 학습`
예: 디지털 운영 전략, AI 자동화 로드맵

## 8. 유형별 필드 = 핵심 기능 (확정 · 일부 미정)

### 8.1 원칙
- 업무 유형마다 **다른 필드**를 가진다(Jira "필드 스킴").
- 유형 × 필드 매트릭스를 한 곳에서 관리(만들기 모달·상세·편집 공통).
- 값이 없어도 **자리(placeholder)는 보여준다**(Jira식 "추가하기").

### 8.2 필드 3층
1. **Jira 순정**: 요약·설명·담당자·보고자·상태·우선순위·라벨·스프린트·스토리포인트
2. **Jira 흔한 관행(커스텀)**: 인수조건(Story), 재현절차·기대/실제·환경(Bug), 체크리스트(Task), 공수
3. **WorkMap 특화**: 현장검증 기록, 관련 솔루션, 운영반영 상태, 막힘 중심

### 8.3 유형 × 필드 매트릭스 (초안 — ○기본 △선택 ✕없음)

| 필드 | Epic | Story | Task | Bug | Sub-task |
|------|------|------|------|------|---------|
| 요약·설명 | ○ | ○ | ○ | ○ | ○ |
| 담당자·보고자 | ○ | ○ | ○ | ○ | ○ |
| 상태·우선순위 | ○ | ○ | ○ | ○ | ○ |
| Epic 연결 | — | ○ | ○ | ○ | (부모 통해) |
| 스토리포인트 | ✕ | ○ | △ | ✕ | ✕ |
| 인수조건 | ✕ | ○ | ✕ | ✕ | ✕ |
| 체크리스트 | ✕ | △ | ○ | △ | △ |
| 공수(예상/실제) | ✕ | ✕ | ○ | △ | ○ |
| 재현절차·기대·실제·환경 | ✕ | ✕ | ✕ | ○ | ✕ |
| 심각도 | ✕ | ✕ | ✕ | ○ | ✕ |
| 하위 진행률 집계 | ○ | ✕ | ✕ | ✕ | ✕ |
| 현장검증 기록 | △ | △ | △ | △ | ✕ |
| 관련 솔루션 | ○ | ○ | △ | ○ | ✕ |

> 위 매트릭스는 **상세 화면 기준**(어떤 유형이 어떤 필드를 갖나).

#### 8.3a 만들기 vs 상세 — 어디서 입력하나 (확정)

> 만들기는 가볍게, 상세는 풍부하게(§9.4). 같은 필드라도 **노출 시점**이 다르다.

| 필드 | 만들기 모달 | 상세 화면 |
|------|:---:|:---:|
| 스페이스·유형·상태·요약·설명 | ○ | ○ |
| 담당자·우선순위·라벨·Epic 연결 | △(선택) | ○ |
| 스토리포인트 / 심각도 | △(필드설정 시) | ○ |
| 인수조건 / 재현절차·기대/실제·환경 / 체크리스트 | ✕ | ○ |
| 공수 / 현장검증 / 측정(목표·실적) | ✕ | ○ |

- 만들기엔 **공통 + 극소수**만. 풍부한 유형별 필드는 **만든 뒤 상세에서** 채운다.
- 빈 칸 강요 금지 — 등록 마찰을 줄여 "안 쓰는 도구"가 되지 않게.

### 8.4 자동/수동 채움 (확정 방향)

| 필드 | 채움 방식 |
|------|----------|
| 스토리포인트 | **수동** (플래닝에서 추정) |
| 공수 예상 | **수동** (시작 전 견적) |
| 공수 실제 | **반자동** (워크로그 기록 → 합산) |
| 진행률(Epic/Story) | **자동** (하위 항목/체크리스트 완료 비율 집계) |

> 원칙: 추정값은 사람이, 누적값은 자동.

### 8.5 목표·실적 측정 추상화 (확정 — WorkMap 차별점)

개발 업무는 "완료/미완료(정성)", 운영 업무는 "50건 중 43건(정량)"으로 목표·실적의 **단위가 다르다**.
이를 별도 모델로 나누지 않고 **하나의 측정 추상화로 통일**한다. (Jira는 기본 미제공 → WorkMap이 정식 제공하는 차별점)

WorkItem은 목표를 `(측정단위 + 목표값 + 현재값)`으로 표현:

| 업무 | 측정단위 | 목표 | 현재 | 진행 |
|------|---------|------|------|------|
| 반품 검수 | 건수 | 50 | 43 | 86% |
| 외주비 절감 | 금액(원) | 3,000,000 | 1,200,000 | 40% |
| 재고 오차율 | 비율(%) | 1 이하 | 1.8 | — |
| API 개발 | 완료여부(정성) | 완료 | 진행중 | 상태 기반 |

- WorkItem 필드: `measureUnitId`(참조) · `targetValue` · `currentValue`
- 진행률 = 현재÷목표 자동 계산 (정성은 상태 기반)
- 개발 업무도 정성(완료여부)으로 같은 칸을 쓴다 → Epic·Story·Task·운영·Goal이 **한 모델**로 묶임

### 8.6 측정 단위 = 관리자 마스터 (확정)

`metricType`을 코드 enum으로 하드코딩하지 않는다. **관리자가 관리하는 마스터 테이블**로 둔다.

```
measure_unit (측정 단위 마스터)
  id
  name        예: 건수 / 금액 / 퍼센트 / 시간 / 완료여부 / 리드타임(일) / SLA(달성·부분·미달)
  valueType   NUMBER | BOOLEAN | SELECT   ← 입력 형태(시스템이 화면 렌더에 사용)
  suffix      예: 건 / 원 / % / 시간
  options     SELECT일 때 선택지
  isSystem    true=시스템 기본(삭제 불가) / false=관리자 추가
```

- **시스템 기본 시드 충분히 제공** → 관리자가 설정 안 해도 바로 쓸 수 있게 (셋업 부담 최소화)
- 새 단위 필요 시 코드 변경 없이 **행 추가** (마이그레이션 불필요)
- 같은 원리를 **커스텀 필드·업무 유형·워크플로 상태**에도 적용 (아래 §12 관리자 설정)

### 8.7 미정 (다음 확정)
- (a) 현장검증을 어느 유형에 정식으로 둘지 (초안: 어디든 △)
- (b) 유형별 필드 차등은 **단일 테이블 + 화면 표시 차등**으로 간다(스키마 차등 없음). 세부 on/off 규칙만 확정 필요.
- (c) **업무 만들기 모달**(§9.4) — 매트릭스 확정 후 모달+상세 동시 반영

## 9. 주요 화면

### 9.1 네비게이션 = 글로벌 LNB 1개 + 프로젝트 상단 가로 탭 (Jira식, 확정)

> **확정(2026-06-23, 실제 Jira 스크린샷 기준):** 좌측 패널은 **글로벌 LNB 1개만**. 프로젝트 내부 뷰 전환(요약/보드/...)은 **본문 상단 가로 탭**으로 둔다. (좌측 2패널이 아님 — 그건 ClickUp/Linear풍)

```
┌─ 글로벌 LNB(1개) ─┬─────────────────────────────────────────────┐
│ 회사홈·받은함      │ 프로젝트 / 반품구조대            ← 브레드크럼     │
│ 최근·즐겨찾기      │ 반품구조대 보드  [멤버][...]    ← 제목+액션      │
│ 계획·대시보드      │ [요약][타임라인][칸반보드][캘린더][보고서]       │
│ 목표·팀           │ [목록][양식][목표][컴포넌트][문서][보관함][+]  ← 가로 탭 │
│ ── 프로젝트 목록 ── │ ──────────────────────────────────────────  │
│  WMS 1.0 구축     │ [검색][필터]              [그룹]  ← 뷰 도구      │
│  반품 운영 안정화   │ 백로그 | 선택됨 | 진행중 | 완료   ← 칸반 컬럼     │
│ 보관함·설정        │                                              │
└───────────────────┴─────────────────────────────────────────────┘
```

- **상단 탭은 고정 아님 — `+`로 추가/제거** (§7 기능 조합과 일치). Jira도 개발/코드(Git연동) 탭 등을 프로젝트마다 다르게 둠.
- **카드 인라인 생성**: 컬럼/리스트에서 "무엇을 완료해야 합니까?" 빈 줄에 바로 입력(모달 없이도). §13.1.
- 칸반 표준 컬럼 예: 백로그 → **개발하기로 선택됨(Selected)** → 진행 중 → 완료. ("Selected" 상태를 §12 워크플로에 포함 검토.)

> **⚠️ 현재 목업 미반영 (코드 그대로, 기획서에만 표시 — 사용자 결정 2026-06-23):**
> 목업은 **좌측 2패널 + "스페이스" 섹션**이라 위 Jira식과 **두 군데** 다르다:
> 1. 프로젝트 탭이 **좌측 2패널** → **상단 가로 탭**으로 바꿔야 함
> 2. **"스페이스" 중간 줄** → **프로젝트 목록**으로 통일(§3)
> LNB는 추후 전면 재작업 예정이라 지금은 코드 미수정. 구현 시 §16 "Space→Project 코드 통합"과 함께 정리.

### 9.2 회사 홈 = 막힘 중심 대시보드 (특화)
- 작은 조직은 진행률보다 **막힌 것 중심**으로 본다.
- 막힌 업무(blockReason) · 지연 · 담당자 없음 · 검토 정체 · 심각 Bug · 현장검증 대기 · 운영반영 대기를 상단에 크게.

### 9.3 업무 상세 (Jira 실제 UI 기준, 유형별 분기)

**유형별 본문 (이미 목업 구현):**
- Epic: 하위 Story/Task/Bug 묶음 + 진행률 집계
- Story: 인수조건 + Sub-task
- Task: 작업 체크리스트 + 공수 + Sub-task
- Bug: 재현절차 / 기대 vs 실제 / 환경 / 심각도
- Sub-task: 부모 링크 + 단순 정보
- **공통(전 유형)**: 연결된 업무 항목(링크) · 관련 문서(임베드) · 첨부 · 댓글 — 유형별 본문 아래 공통으로 붙음.

**상세 화면 구조 (Jira 스크린샷 기준, 확정 · 일부 미구현):**
```
[epic 추가] / ZGOH-2   [↑][↓]                    [🔒][👁1][공유][⋯]
3333 (제목, 인라인 편집)
[+ 액션메뉴] [⋯]
─── 본문 ───            ─── 우측 패널(접이식 섹션) ───
설명 / 유형별 필드        ▾ 세부 사항          [⚙ 구성]
하위 작업(부모-자식)        기한·레이블·Team·시작일
연결된 업무 항목(링크)      Sprint·Story point·보고자
관련 문서(임베드)          ▾ 개발 (Git 연동)
첨부·웹링크                ▾ 자동화 (규칙 실행)
댓글                     ───
                        만듦 4분 전 / 업데이트 4분 전
```

- **상단 `+` 액션 메뉴**(§13.1): 하위작업(⇧C)·업무연결(⇧K)·첨부·웹링크·추천첨부·메뉴검색.
- **위/아래 화살표**(↑↓): 목록 내 이전/다음 항목으로 이동.
- **워치(👁)**: 구독 + 구독자 수. **공유** 버튼.
- **하위 작업 ≠ 연결된 업무 항목 (별개 섹션, 2026-06-23 에픽 화면 확인)**:
  - **하위 작업** = 부모-자식 계층(Epic→Story, Story→Sub-task). 진행률 집계 대상.
  - **연결된 업무 항목** = 계층과 무관한 링크(blocks / blocked by / relates to / duplicates). §13.1 이슈 링크의 상세화면 위치가 여기.
- **관련 문서(임베드 슬롯)**: 항목 본문에서 관련 문서를 끌어 거는 자리(Jira의 Confluence 콘텐츠 슬롯에 대응). **우리는 자체 문서탭(§13.5)/외부 웹링크**를 임베드한다(외부 위키 종속 없음). §13.7.3 문서(Docs)와 연결.
- **우측 패널 = 접이식 섹션**: 세부사항 / 개발(Git) / 자동화. 한 덩어리 아님.
- **`구성`(⚙)**: 이 화면에 보일 필드 설정 바로가기(§13.5 필드 스킴).
- **만듦/업데이트 시각** 표시.
- **제목 인라인 편집**, 모든 필드 인라인 수정.

### 9.4 업무 만들기 모달 (Jira 실제 UI 기준, 확정 · 미구현)

> **원칙: 만들기는 가볍게, 상세는 풍부하게 (확정 2026-06-23).**
> Jira는 만들기 모달에 유형 바꿔도 필드가 **크게 안 달라진다**(실측 — 사용자 화면 확인). 만들기는 최소 필드로 빠르게, 유형별 풍부한 필드(인수조건/재현절차/체크리스트)는 **만든 뒤 상세 화면**에서 채운다.
> 근거: 만들 때 빈 칸을 강요하면 사람이 등록 자체를 안 한다(= "도구가 현장을 막으면 버린다", §11).

**만들기 UI는 유형이 뭐든 동일한 모달 하나.** 제목만 "에픽 만들기/스토리 만들기"로 바뀜.

```
에픽 만들기                                    [_][⤢][⋯][×]
필수 필드는 별표(*)로 표시
─────────────────────────────────────────
스페이스(프로젝트) *  [반품구조대 ▾]
업무 유형 *          [에픽 ▾]
─────────────────────────────────────────
상태                [할 일 ▾]  "만들 때의 초기 상태"  ← 워크플로 시작상태(§12)
요약 *              [____________________]
설명                [리치 에디터: 굵게·리스트·이미지·코드·이모지·링크·실행취소]
(선택) 담당자 · 우선순위 · 라벨 · Epic 연결
─────────────────────────────────────────
[ ] 다른 항목 만들기              [취소] [만들기]
```

- **만들기 모달 = 거의 공통**: 스페이스 · 유형 · 상태(초기) · 요약 · 설명 + (선택) 담당자/우선순위/라벨/Epic.
- 유형별 차이는 **최소** — 기껏해야 Bug 심각도, Story 포인트 정도(필드 설정에서 켜면 노출). 그 외 유형별 필드는 모달에 안 넣음.
- **풍부한 유형별 필드는 §9.3 상세 화면에서** (Story 인수조건 / Bug 재현·기대/실제 / Task 체크리스트 등).
- **설명 = 리치 에디터** (굵게/리스트/이미지/코드블록/이모지/링크/실행취소). `⌘+/` 단축키.
- **"다른 항목 만들기" 체크**: 연속 생성(모달 유지).
- 진입: 헤더 `[만들기]` · 각 영역 `+ 만들기`(인라인) 둘 다.

> 즉 §8.3 매트릭스는 **"상세 화면 기준"**. 만들기 모달에는 그중 공통+극소수만 노출(§8.3a).

### 9.5 목록 뷰 — 분할 화면 (Jira 실제 UI 기준, 확정 · 미구현)

> 목록 뷰는 두 모드 토글(우상단): **① 전체 목록(표)** ⇄ **② 분할 화면**.
> 분할 = 좌측 항목 리스트 + 우측 상세 패널(§9.3)을 한 화면에. 리스트에서 클릭하면 우측이 즉시 갱신 → 페이지 이동 없이 연속 처리.
- 좌측 리스트: 사용자 지정 필드로 컬럼/정렬, 항목 클릭 → 우측 상세.
- 우측: §9.3 상세(접이식 섹션) 그대로.

## 10. WorkMap 특화 기능

### 10.1 관련 솔루션
- 솔루션(WMS/OMS/반품구조대/AI 솔루션/자동화 설비/쇼핑몰)은 계층이 아닌 **연결 정보**.
- 프로젝트·업무 항목에 복수 연결 가능.

### 10.2 현장검증 기록
- 단순 체크박스 아님. 별도 기록: 검증자/검증일/장소/환경/테스트 내용/결과/발견 이슈/후속 업무.
- 결과에 따라 상태 전이: 개발완료 → 현장검증중 → 운영반영완료.

### 10.3 운영반영 상태
- 개발 완료와 운영 반영을 분리: 개발완료 / 테스트완료 / 현장검증중 / 운영반영완료.

### 10.4 막힘 중심 관리
- 업무 항목에 BLOCKED 상태 + 차단 사유 필수. 대시보드에서 강조.

## 11. 강제 vs 권장 (확정)

- **시스템 강제**: 계층 정합성만 (Sub-task는 부모 필수, Epic은 Sub-task 부모 불가 등).
- **강제 금지**: "Story 먼저 → Task 달기" 식 워크플로 강제 안 함. 도구가 현장을 막으면 버려진다.
- 가이드: 개발형은 Epic>Story>Task 권장, 운영형은 Task/요청 위주. 유형 5종 항상 제공, 순서는 사람이 선택.

|------|------|

## 13. 전체 기능 명세 (Jira 동급 + WorkMap 특화)

> 설계 단계에서 빠짐없이 정의한다. 우선순위: **P1=실전 1차 필수 / P2=실전 안정화 / P3=이후 확장**.

### 13.1 업무 항목 동작 (Work Item Actions)

#### 13.5a 양식 빌더 (Jira Form 기준, 확정 · 미구현)

> 우리 §13.3 "양식(Form)"의 실제 모습 = **드래그앤드롭 양식 빌더**. 외부/현장 요청을 받아 제출 시 업무 항목 자동 생성. 필드 마스터(§8.6)·필드 스킴(§13.5)과 한 묶음 — 양식이 그 필드들을 소비한다.

```
[에픽 ▾] 스페이스 반품구조대 - 에픽 양식    [🔒][공유][내보내기][⋯]  "모든 변경 저장됨"
도움말 텍스트…
┌─ 요약 *            "설명 추가" [답변 입력] ┐      우측: 필드 팔레트
├─ 설명              "설명 추가" [답변 입력] │      ⠿ Sprint
├─ 첨부 파일         [업로드]               │      ⠿ Story point
└─ (드래그로 필드 추가)                     ┘      ⠿ Team / 기한 / 담당자
                                                 ⠿ 레이블 / 상위항목 / 시작날짜
                                                 [+ 새 필드 만들기]
                                                 [양식 필드 관리]
```

- **양식 = 업무 유형과 연결** (좌상단 "에픽 ▾"). 제출 시 그 유형의 업무 항목 생성.
- **우측 필드 팔레트 → 좌측으로 드래그**해 양식 구성. 필드 순서도 드래그(⠿).
- 필드는 **필드 마스터에서 가져오며**, "새 필드 만들기"·"양식 필드 관리"로 마스터 직접 추가/관리(§8.6).
- 각 필드에 **도움말/지침 텍스트**, 필수(*) 지정.
- **자동 저장**, 잠금/공유/내보내기.
- 제출 양식은 외부 게스트도 채울 수 있게 공유 가능(요청 접수 창구).

### 13.8 첫 활용 시나리오 (안개 걷기 — 설계 의도)

> 본 플랫폼의 1차 목적은 신규 업무 관리가 아니라 **"3월 이후 한 일의 현황 재정리"**.

1. **인벤토리화**: 반품구조대/WMS 등 지금까지 만든 기능을 전부 업무 항목으로 등록
2. **상태 냉정 재분류**: 완료/구현됨·미검증/운영테스트 필요/수정 필요/재설계 필요/후순위
3. **완료 기준 재정의**: 개발 완료 ≠ 업무 완료 (운영검증까지 포함, §10.3)
4. **1~2주 안정화 계획**: 이번 주 포함 + **"이번 주 제외"** 명시(범위 확산 방지)
5. **운영검증 → 다음 Backlog**: 검증 결과를 다음 개발 항목으로 전환(§13.4)

|------|------|:---:|------|
| **기본 필터(필드 기반)** | 유형·상태·담당자·우선순위·라벨·스프린트·Epic·기한·막힘여부로 거르기(다중 선택) | **P1** | 버튼만 |
| **전체 텍스트 검색** | 제목·설명·댓글 키워드 검색 | **P1** | 버튼만 |
| **퀵필터(보드/목록 토글)** | "내 항목 / 최근 업데이트 / 막힌 것 / 미배정" 등 빠른 토글 | **P1** | 없음 |
| **저장된 필터(Saved Filter)** | 자주 쓰는 조건 저장·이름 부여·재사용 | P2 | 없음 |
| **공유 필터** | 저장 필터를 팀/프로젝트에 공유 | P2 | 없음 |
| **고급 쿼리(JQL류)** | 조건식(AND/OR, 비교, 정렬)으로 정밀 검색 — Jira JQL 경량판 | P3 | 없음 |
| **정렬·그룹·컬럼 설정** | 목록 뷰에서 정렬 기준·그룹핑·표시 컬럼 사용자 지정(§9.5) | P2 | 시각만 |

- 필터 모델은 측정·필드 마스터(§8.6)·필드 스킴(§13.5)과 정합 — 거를 수 있는 필드 = 그 항목이 가진 필드.
- 받은함(§13.7.1)·회사 홈(§9.2)·벌크 편집(§13.1)은 "저장된 필터"를 재료로 쓸 수 있다.

## 14. 데이터 모델 스케치 (구현 진입 기준)

> 핵심만. 상세 컬럼은 구현 시 T3-1 데이터 모델로 확정.

```
workspace (1) ─< project (N)
project ─< work_item (N)            # Epic/Story/Task/Bug/Sub-task 단일 테이블
work_item.parent_id → work_item     # 계층 (Epic→Story→Sub-task)
work_item.measure_unit_id → measure_unit   # 목표·실적 측정 (§8.5/8.6)
project ─< sprint / release / goal / risk / decision / learning
work_item ─< comment / attachment / worklog / activity_log / field_verification
work_item >< dependency >< work_item       # 의존성(양방향)
```

### 단일 work_item 핵심 컬럼 (요지)
- 정체성: id, key, issue_type, project_id, parent_id, epic_id
- 공통: title, description, status, priority, assignee_id, reporter_id, start_date, due_date
- 측정: measure_unit_id, target_value, current_value, progress(자동)
- 애자일: sprint_id, story_points, estimate_hours
- 유형 고유(값 없으면 비움, 화면 표시만 차등 — §8.1):
  acceptance_criteria(Story) / steps_to_reproduce·expected·actual·environment·severity(Bug) / checklist(Task)
- 특화: block_reason, related_solutions, ops_apply_status, is_field_verified

### 마스터(관리자 관리, 시스템 시드)
- measure_unit (§8.6) · field_scheme(유형/프로젝트별 표시필드) · workflow(상태·전이) · issue_type · role_permission · project_template

## 15. 세션 인수인계 요약 (이 문서만으로 이어가기)

> 이 절만 읽어도 새 세션에서 바로 이어갈 수 있도록. 위 본문의 결론을 한 곳에 모음.

### 15.1 확정된 결정 (변경하려면 근거 필요)
1. 벤치마크 = **Jira 애자일 + 물류 현장 특화**. ClickUp(v0.3) 폐기.
2. 계층 = **워크스페이스 > 프로젝트 > Epic > Story/Task/Bug > Sub-task**. "스페이스=프로젝트"로 통일(용어: 프로젝트).
3. depth: Epic(0) → Story/Task/Bug(1, 형제) → Sub-task(2).
4. 백로그/스프린트 = **같은 구조**, 차이는 "이번 주기에 담았나"(계획 단위)이지 실행 여부 아님. 실행상태는 별도 축.
5. 유형별로 **다른 필드**(필드 스킴). **단일 테이블 + 화면 표시 차등**(스키마 차등 없음). 값 없어도 placeholder 표시.
6. 목표·실적 = **측정 추상화**(측정단위 + 목표값 + 현재값). 개수·금액·%·정성 다 커버. 개발=정성, 운영=정량, 같은 모델.
7. 측정단위·커스텀필드·워크플로·업무유형 = **관리자 마스터 데이터**(하드코딩 금지, 시스템 시드 제공).
8. 자동/수동: 추정값(포인트·예상공수)=수동, 누적값(실제공수·진행률)=자동.
9. 강제는 **계층 정합성만**. "Story 먼저" 같은 워크플로 강제 금지.
10. 첫 활용 = **안개 걷기**(3월 이후 한 일 인벤토리화 → 상태 재분류 → 1~2주 안정화 → 운영검증 → 다음 백로그). §13.8.
11. 운영형 "처리량 관리"는 **별도 모델 불필요** — work_item + 측정 추상화로 표현.
12. 첫 시뮬레이션 대상 = **반품구조대 1차 운영 안정화**.
13. CRUD 모달·인라인편집·드래그앤드롭은 **당연히 포함**(기본 전제, §13.1).
14. **채널 소통 = 독립 채널 + 업무 연결**로 정식 보유(§13.7.2). **axopm `opm-comm` 모듈 이식**이 전제(WebSocket·읽음·스레드·반응·타이핑 이미 구현). 차별점 = "메시지 → 업무 전환/핀". 제 초기 "채팅은 제품 삼킴" 판단은 실측으로 철회됨(axopm에 이미 구현돼 있음).
15. **네비게이션 = 글로벌 LNB 1개 + 프로젝트 상단 가로 탭(Jira식)**(§9.1). 좌측 2패널 아님. 탭은 `+`로 추가/제거(고정 아님). 현재 목업은 좌측 2패널+스페이스 섹션이라 미반영(LNB 재작업 시 정리).
16. 칸반 표준 컬럼에 **"개발하기로 선택됨(Selected)"** 상태 포함 검토(§12). 카드 인라인 생성 지원.
17. **만들기는 가볍게, 상세는 풍부하게**(§9.4, §8.3a). Jira 실측 — 만들기 모달은 유형 바꿔도 필드 거의 동일(공통+극소수). 인수조건·재현절차 등 유형별 풍부한 필드는 상세에서. 빈 칸 강요 금지.
18. **목록 분할뷰**(§9.5, 좌리스트+우상세), **상세 우측 접이식 섹션·`+`액션메뉴·워치·구성**(§9.3, §13.1), **Team 필드**(§13.1) 추가.
19. **AI 기능(AI에게 물어보기·AI 빠른답변 댓글)은 지금 제외**(사용자 결정) — 별도 축(FlowGuard/aimbase)에서 다룸. WorkMap 기획엔 넣지 않음.
20. **Jira 대비 누락 4건 보완 반영**(2026-06-23): ① 검색·필터·뷰 도구 §13.9 신설(기본필터/전문검색/퀵필터 P1) ② 벌크 편집·유형 전환 §13.1 추가(P1, 안개 걷기 직결) ③ 항목 이동(프로젝트 간) §13.1(P2) ④ 프로젝트 가시성·멤버 초대 §13.5 추가(P1). "누가 뭘 보나"와 "대량 재분류"가 1차 목적에 직결되어 P1로 승격.
21. **에픽 화면 캡처(2026-06-23)에서 드러난 상세화면 누락 2건 §9.3 반영**: ① **하위 작업 ≠ 연결된 업무 항목** — 부모-자식 계층과 링크(blocks/relates)는 별개 섹션(이슈 링크의 상세화면 위치 명기) ② **관련 문서 임베드 슬롯** — Jira Confluence 콘텐츠 자리에 우리는 자체 문서탭/외부 웹링크를 임베드(§13.7.3 P2). 둘 다 전 유형 공통 본문 섹션.

### 15.2 아직 정할 것 (미정)
- (a) 현장검증을 어느 유형에 정식으로 둘지 (초안: 어디든 △)
- (b) 유형별 필드 on/off 세부 규칙 (방식은 단일테이블+화면차등으로 확정)
- (c) 업무 만들기 모달 화면 설계

### 15.3 더 큰 맥락 (사용자 의도)
- 회사 전체 방향: 모든 개발은 두 축으로 통제 — **관리·계획 = WorkMap(이 문서, Jira식)**, **개발 통제 = FlowGuard**.
- 현재 단계는 **관리·계획 축(WorkMap)만** 논의 중. FlowGuard와 섞지 않는다.
- 문제의식: "3월부터 AI로 빨리 달렸는데 뚜껑 열어보니 정리가 안 됨(안개)". WorkMap의 1차 목적이 이 안개 걷기.

### 15.4 구현 진입 판단 (현재)
- **기획 방향 = 확정.** 구현 진입 조건 거의 충족.
- 진입 전 권장 1단계: **반품구조대 1차 안정화를 목업/문서에 시뮬레이션** → 미정 (a)(b)(c)가 자연히 드러남.
- 구현 1순위(P1): 상태 전이 / 측정 추상화 / 관리자 설정(측정단위·필드스킴·워크플로) / 막힘중심 홈 / 알림 / **검색·필터(§13.9) / 벌크 편집·유형 전환(§13.1) / 프로젝트 가시성·멤버 초대(§13.5)**.
