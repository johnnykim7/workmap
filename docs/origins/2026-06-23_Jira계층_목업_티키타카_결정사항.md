## 1. 계층 구조 (확정)

```
워크스페이스 > 프로젝트 > Epic > Story / Task / Bug > Sub-task
```

- **"스페이스 = 프로젝트"로 통일.** 별도 스페이스 계층을 두지 않는다.
  - 근거: Jira의 실질 단위는 프로젝트이며 보드·백로그·스프린트·릴리스가 전부 프로젝트에 종속.
    우리 데이터도 스페이스 1 : 프로젝트 1에 가까워 중간 계층이 과함.
  - 용어는 화면에 **"프로젝트"** 로 표기 (추후 "업무"/"업무공간" 등으로 바꿀 수 있음).
- **Story · Task · Bug는 같은 depth(형제).** 셋의 차이는 깊이가 아니라 성격.
- **Sub-task만 그 아래 한 단계.** Story/Task/Bug 누구든 부모가 될 수 있음.
- depth 정리: Epic(0) → Story/Task/Bug(1) → Sub-task(2)

> 주의: 위 계층 전환은 인사이트로 확정했으나 코드 레벨 통합(Space→Project)은 미완.
> 현재 코드는 여전히 `spaces`/`/spaces/:id/*` 경로를 사용. 구현 시 프로젝트로 일원화 필요.

## 2. Story vs Task (확정)

| | Story | Task |
|---|-------|------|
| 관점 | 사용자/현장의 가치 | 그 가치를 만드는 작업 |
| 예 | "작업자로서 바코드로 입고 상품을 조회할 수 있다" | "상품 조회 API 개발" |
| 완료 기준 | 인수조건(그 행동을 할 수 있음) | 작업물 완성 |
| 스토리포인트 | 보통 매김 | 잘 안 매김 |

- 보통 Story 1개 밑에 Task 여러 개. 단 **강제하지 않음.**

## 3. 백로그 / 스프린트 (확정)

- **둘은 같은 구조**(같은 업무 항목을 담음). Jira 백로그 화면 안에 스프린트 영역 + 백로그 영역이 함께.
- 차이는 **"실행 여부"가 아니라 "계획 단위"**:
  - 백로그 = 아직 이번 주기에 안 담은 대기 목록
  - 스프린트 = 이번 주기에 하기로 담은 묶음
- 실행 상태(TODO/진행중/완료)는 **별도 축**으로 항목 자체가 가짐.
- 보드 화면(`/board`)은 현재 스프린트만 칸반으로(실행용), 백로그 화면은 계획용.

## 4. 유형별 필드 = 핵심 기능 (확정 · 일부 미정)

### 4.1 결정
- 업무 유형마다 **다른 필드**를 가진다. Jira의 "필드 스킴"에 해당.
- 필드 표시는 **유형 × 필드 매트릭스**로 한 곳에서 관리(모달·상세·편집 공통).
- 값이 없어도 **자리(placeholder)는 보여준다** (Jira식 "설명 없음 / 추가하기").
  - 현재 목업은 "값 있으면 섹션 표시, 없으면 사라짐" → 구현 시 placeholder 방식으로 변경 필요.

### 4.2 필드 3층 분류
1. **Jira 순정**: 요약·설명·담당자·보고자·상태·우선순위·라벨·스프린트·스토리포인트
2. **Jira 흔한 관행(커스텀으로 추가)**: 인수조건(Story), 재현절차·기대/실제·환경(Bug), 체크리스트(Task), 공수
3. **WorkMap 특화**: 현장검증 기록, 관련 솔루션, 운영반영 상태, 막힘 중심

### 4.3 유형 × 필드 매트릭스 (초안 — ○기본 △선택 ✕없음)

| 필드 | Epic | Story | Task | Bug | Sub-task |
|------|------|------|------|------|---------|
| 요약·설명 | ○ | ○ | ○ | ○ | ○ |
| 담당자·보고자 | ○ | ○ | ○ | ○ | ○ |
| 상태·우선순위 | ○ | ○ | ○ | ○ | ○ |
| Epic 연결 | — | ○ | ○ | ○ | (부모 통해) |
| 스토리포인트 | ✕ | ○ | △ | ✕ | ✕ |
| 인수조건 | ✕ | ○ | ✕ | ✕ | ✕ |
| 체크리스트 | ✕ | △ | ○ | △ | △ |
| 공수(예상/실제) | ✕ | ✕ | ○ | △ | ○ |
| 재현절차·기대·실제·환경 | ✕ | ✕ | ✕ | ○ | ✕ |

### 4.4 미정 (다음 확정 필요)
- (a) **현장검증을 어느 유형에 정식으로 둘지** (현재 초안: 어디든 △)
- (b) **매트릭스가 프로젝트 유형(개발/운영/계획)에 따라 또 달라지나** (예: 운영 프로젝트는 스토리포인트·인수조건 끄기)
- (c) **업무 만들기 모달**(기획서 5.4) 미구현 — 매트릭스 확정 후 모달+상세 동시 반영

## 5. 강제 vs 권장 (확정)

- **시스템 강제**: 계층 정합성만 (Sub-task는 부모 필수, Epic은 Sub-task의 부모 불가 등).
- **강제 금지**: "Story 먼저 만들고 Task를 달아라" 식 워크플로 강제 안 함.
  - 근거: 도구가 현장을 막으면 버려진다. 쓸 수 있게 열되 안 써도 굴러가야 함(전역 FlowGuard 원칙 — 확 와닿음/정방향 효용).
- 운영 가이드:
  - 개발 프로젝트: Epic > Story > Task **권장**(템플릿/가이드), 강제 X
  - 운영 프로젝트: Task/요청 위주, Story 거의 안 씀
  - 유형 5종(Epic/Story/Task/Bug/Sub-task)은 항상 제공, 순서는 사람이 선택

## 6. 목업 현재 상태 (구현된 것)

- 타입/데이터: Jira 구조(워크스페이스/스페이스/프로젝트/Epic/Story/Task/Bug/Sub-task), WMS 입고 관리 샘플 4계층 완성
- 사이드바: 2패널(글로벌 + 스페이스 내부 유형별 탭)
- 화면 30+개: 회사홈(막힘 중심)·보드·백로그(Epic 펼침 트리)·타임라인·릴리스·보고서·목록·캘린더·양식·승인·문서·목표·리스크·결정·학습·플랜·의존성·프로젝트개요·업무상세(유형별 분기)
- 유형별 상세 분기: Epic(하위 집계)/Story(인수조건)/Task(체크리스트·공수)/Bug(재현·기대/실제)
