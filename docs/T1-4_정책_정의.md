## v0.4 핵심 전환 — "정책 = 관리자 마스터 데이터"

v0.4의 본체는 **관리자가 코드 변경 없이 다루는 마스터 데이터**다(기획서 §8.6 "코드 변경 0").
측정단위·필드스킴·워크플로·업무유형을 enum으로 하드코딩하지 않고 **마스터 테이블**로 둔다. 새 단위·새 상태·새 유형이 필요하면 마이그레이션이 아니라 **행 추가**로 확장한다.
따라서 v0.4의 정책(POL-xxx)은 대부분 "변경 가능"이며, 그 변경 수단이 application.yml이 아니라 **마스터 테이블 + 관리자 설정 화면(WMP-ADM-xxx)** 인 점이 v0.3과 다르다.

> 정책 = 변경 가능한 규칙. 비즈니스 규칙(T1-3)은 코드에 고정, 정책(T1-4)은 설정/마스터로 관리.

## 정책 목록

### POL-001 | 워크플로 정의 정책(상태/전이)
- **적용 모듈**: H. 관리자 설정 / C. 업무 항목(상태)
- **정책 설명**: 업무 유형/프로젝트별 상태 목록과 전이(transition) 화이트리스트를 `workflow` 마스터로 정의한다(기획서 §12, §13.5). 시스템 기본 시드 제공 후 관리자가 워크플로 편집기(WMP-ADM-003)로 편집.
  - 개발형: 할 일 → 진행 중 → 검토 중 → 완료
  - 운영형: 접수 → 확인 중 → 처리 중 → 현장확인 → 완료 / 보류
  - 현장검증형: 할 일 → 진행 중 → 개발완료 → 현장검증중 → 운영반영완료
  - 공통: BLOCKED(차단 사유 필수) — 어느 워크플로에서나 진입 가능
  - 칸반 표준 컬럼에 "개발하기로 선택됨(Selected)" 포함 검토(기획서 §9.1, §15.1-16)
- **변경 가능 여부**: 가능. 상태/전이 추가·삭제·재배치는 워크플로 마스터의 데이터 변경(코드 변경 없음). FSM 화이트리스트(BIZ-010)의 **데이터 소스**가 곧 이 마스터다. Phase 1은 시드 제공 + 편집 가능.
- **관련 기능 ID**: WMP-WI-007, WMP-ADM-003, WMP-AGL-005, WMP-OPS-001

### POL-002 | 지연 판단 정책
- **적용 모듈**: G. 회사홈/보고
- **정책 설명**: 지연 = `due_date < today` AND 항목 상태가 제외 집합에 없음. 제외 집합 기본값 = {완료, 취소}. 보류(보류/BLOCKED)를 지연에서 뺄지는 `delay.exclude-statuses` 설정으로 조정. 워크플로별 상태명이 다르므로(POL-001) 제외 집합은 **공통상태 의미(완료/취소 계열)** 기준으로 매핑한다.
- **변경 가능 여부**: 가능 (제외 상태 집합 설정)
- **관련 기능 ID**: WMP-HOME-002, WMP-HOME-001

### POL-003 | 장기 미변경(정체) 기준 정책
- **적용 모듈**: G. 회사홈/보고
- **정책 설명**: `status_changed_at`이 N일 이상 갱신되지 않으면 "장기 미변경(정체)"으로 표시(기획서 §9.2 막힘 중심). 기본값 N=7일. `stale.threshold-days` 설정으로 변경. 회사 홈의 "검토 정체"·정체 지표의 판정 기준.
- **변경 가능 여부**: 가능 (일수 설정)
- **관련 기능 ID**: WMP-HOME-001, WMP-HOME-002

### POL-004 | 권한/역할 매트릭스 정책
- **적용 모듈**: 전역 / B. 워크스페이스·프로젝트
- **정책 설명**: Owner/Admin/Manager/Member/Viewer 5역할의 행위별 권한을 `role_permission` 마스터로 관리(기획서 §13.5). 사용자 초대·워크스페이스/프로젝트 생성·멤버 관리·타인 업무 상태 변경·삭제·회사홈 조회 등 액션×역할.
  - 프로젝트 **가시성**(PUBLIC=워크스페이스 전체 / PRIVATE=멤버만)을 가시성 축으로 함께 둔다(기획서 §13.5, WMP-WS-006).
  - 담당자·보고자·@멘션 대상은 **프로젝트 멤버**만(WMP-WS-005).
  - Phase 1은 단순 권한, 이슈 수준 보안(항목별 열람 제한)은 Phase 3.
- **변경 가능 여부**: 제한적 (역할 신규 추가는 설계 변경, 역할×액션 매핑은 마스터 설정으로 변경)
- **관련 기능 ID**: WMP-AUTH-004, WMP-AUTH-005, WMP-WS-002, WMP-WS-005, WMP-WS-006

### POL-005 | 측정 단위 마스터 정책
- **적용 모듈**: H. 관리자 설정 / C. 업무 항목(측정)
- **정책 설명**: 목표·실적 측정 단위를 `measure_unit` 마스터로 관리(기획서 §8.6). `metricType`을 enum으로 하드코딩하지 않는다.
  - 컬럼: `name`(건수/금액/퍼센트/시간/완료여부/리드타임/SLA 등) · `valueType`(NUMBER | BOOLEAN | SELECT — 화면 렌더 형태) · `suffix`(건/원/%/시간) · `options`(SELECT 선택지) · `isSystem`(true=시스템 기본)
  - 진행률 = 현재÷목표(정량) 또는 상태 기반(정성). 개발=정성, 운영=정량을 한 모델로(기획서 §8.5).
- **변경 가능 여부**: 가능. 시스템 기본 시드 충분 제공(셋업 없이 즉시 사용), 새 단위는 **행 추가**(마이그레이션 불필요). `isSystem=true`는 삭제 불가.
- **관련 기능 ID**: WMP-ADM-001, WMP-WI-016, WMP-OPS-002

### POL-006 | 필드 스킴 정책
- **적용 모듈**: H. 관리자 설정 / C. 업무 항목
- **정책 설명**: 유형/프로젝트별 **표시 필드 on/off**를 `field_scheme` 마스터로 관리(기획서 §8.1, §13.5). 스키마는 단일 work_item 테이블이며 **화면 표시만 차등**(스키마 차등 없음, BIZ-102).
  - 값이 없어도 자리(placeholder)는 표시(기획서 §8.1 "추가하기").
  - 유형 전환(WMP-WI-014) 시 미사용 유형 고유 필드는 데이터 보존(비표시).
  - 양식 빌더(WMP-ADM-005)·검색 필터(WMP-VIEW-004)가 이 스킴을 소비 — 거를 수 있는 필드 = 항목이 가진 필드.
- **변경 가능 여부**: 가능 (유형/프로젝트별 표시 필드 on/off 설정)
- **관련 기능 ID**: WMP-ADM-002, WMP-WI-001, WMP-WI-004, WMP-WI-014

### POL-007 | 업무 유형 마스터 정책
- **적용 모듈**: H. 관리자 설정
- **정책 설명**: 업무 유형을 `issue_type` 마스터로 관리(기획서 §13.5). 5종 기본(Epic/Story/Task/Bug/Sub-task)은 시스템 기본, 추가 유형(운영요청/승인요청/현장검증 등)은 관리자가 등록.
  - 계층 depth 규칙 준수: Epic(0) → Story/Task/Bug(1) → Sub-task(2)(기획서 §3.1, BIZ-103).
- **변경 가능 여부**: 가능 (유형 추가). 단, 5종 시스템 기본은 **삭제 불가**, 계층 depth 규칙은 코드 고정.
- **관련 기능 ID**: WMP-ADM-004, WMP-WI-001, WMP-WI-005, WMP-WI-014

### POL-008 | 우선순위 체계 정책
- **적용 모듈**: C. 업무 항목
- **정책 설명**: 긴급/높음/보통/낮음 4단계. 정렬·집계(회사 홈 막힘/지연 우선표시)의 가중치로 사용. 단계 추가·명칭 변경·정렬 가중치는 설정으로 관리.
- **변경 가능 여부**: 가능 (단계/명칭/가중치)
- **관련 기능 ID**: WMP-WI-008, WMP-HOME-001

### POL-009 | 알림 트리거 정책
- **적용 모듈**: I. 알림
- **정책 설명**: 알림 발행 트리거(기획서 §13.7.1). "행동이 필요한 경우에만" 발행.
  - 트리거: 업무 배정 · 댓글 @멘션 · 마감 임박(기본 1일 전) · 마감 초과 · 막힘(BLOCKED) 상태 변경.
  - 마감 임박 기준일수(`notify.due-soon-days`, 기본 1), 트리거별 on/off, 일일 요약 여부는 설정.
- **변경 가능 여부**: 가능 (트리거 on/off, 임박 일수)
- **관련 기능 ID**: WMP-NOTI-001, WMP-NOTI-002, WMP-WI-006, WMP-WI-009

### POL-010 | 프로젝트 유형 템플릿 정책
- **적용 모듈**: B. 워크스페이스·프로젝트
- **정책 설명**: 프로젝트 유형(개발형/운영형/계획형) 프리셋과 기본 탭(뷰) 조합을 `project_template` 마스터로 관리(기획서 §7). 유형은 기능 조합의 **출발점**이며 탭은 켜고 끌 수 있다.
  - 개발형: Backlog · Sprint · Scrum Board · Timeline · Release · Report · 문서
  - 운영형: Kanban Board · List · Calendar · Form · Approval · 첨부 · 문서 · Report
  - 계획형: Goal · Plan · Timeline · Dependency · Risk · Decision · 학습
- **템플릿이 묶는 범위**: 탭 조합(default_tabs) + 워크플로(default_workflow_id) + **업무 유형 목록(issue_type_codes)** + 필드 스킴. (Jira 템플릿과 동일 범위)
- **추가/수정 방법**: **전용 관리 화면·API를 만들지 않는다(사용자 결정 2026-06-23).** 빈도 낮은 운영 작업이므로 **DB 직접 INSERT/UPDATE 또는 Flyway 시드 SQL**로 처리. is_system=false 행을 직접 넣으면 즉시 새 유형으로 노출(코드/배포 불필요). 측정단위·필드스킴·워크플로(관리자 화면 보유)와 달리 템플릿은 DB 직접 운영.
- **변경 가능 여부**: 가능 (DB 직접) — 프리셋 정의 + 프로젝트별 탭 조합 편집(생성 후)
- **관련 기능 ID**: WMP-WS-002, WMP-WS-004

### POL-011 | 승인 정책
- **적용 모듈**: C. 업무 항목(상태) / H. 관리자 설정
- **정책 설명**: 승인 게이트 상태(`workflow_status.is_approval=true`)에서 승인자가 APPROVE/REJECT를 처리해야 다음 단계로 진행한다(BIZ-110/111). 게이트 진입 시 승인 행(PENDING) 생성, 처리 결과에 따라 전진/반려. 다음 항목을 정책으로 조정한다.
  - **다수 승인 방식**: 전원 동의(AND) vs 1인 동의(OR). **기본 = 전원 동의(전원 APPROVED 시 통과)**.
  - **요청자 자기승인 허용 여부**: 요청자 본인이 승인자에 포함될 때 자기 승인 가능 여부. 기본 = 불허(설정으로 허용 가능).
  - **거부 시 복귀 상태**: REJECT 시 work_item이 돌아갈 상태. **기본 = 게이트 진입 직전 상태**, 지정 상태로 변경 가능.
  - **승인 SLA(선택)**: 승인 대기 기준 시간/일수. 초과 시 정체 표시·알림 대상(선택 설정).
- **변경 가능 여부**: 가능 (승인 방식·자기승인·복귀 상태·SLA 설정 — 워크플로/관리자 마스터)
- **관련 기능 ID**: WMP-OPS-005, WMP-OPS-006

## 정책 vs 비즈니스 규칙 구분 기준

- **비즈니스 규칙 (T1-3)**: 변하지 않는 핵심 규칙. 예) "Task는 업무영역 필수(BIZ-001)", "삭제는 소프트(BIZ-009)", "FSM 화이트리스트만 전이(BIZ-010)", "계층 정합성(BIZ-103)".
- **정책 (T1-4)**: 변경 가능한 규칙. 예) "워크플로 상태/전이 정의(POL-001)", "지연 제외 상태 집합(POL-002)", "장기 미변경=7일(POL-003)", "측정 단위 마스터(POL-005)".

**v0.4 구분의 핵심**: 비즈니스 규칙은 **"규칙의 형태"**(FSM은 화이트리스트여야 한다)를 고정하고, 정책은 그 규칙의 **"내용"**(화이트리스트의 실제 상태·전이 목록)을 마스터 데이터로 둔다. 예) BIZ-010은 "화이트리스트만 허용"(고정), POL-001은 "그 화이트리스트가 무엇인가"(워크플로 마스터, 변경 가능).

구현 시 차이: 비즈니스 규칙은 코드에 고정. 정책은 마스터 테이블(measure_unit / field_scheme / workflow / issue_type / role_permission / project_template) 또는 application.yml로 관리하여 코드 변경 없이 바꿀 수 있게 한다(기획서 §8.6 "코드 변경 0").

**명명 규칙**: 정책 ID 형식: `POL-[순번]` (예: POL-001)
