# WorkMap 기술 스택 결정서

> 설계 버전: 2.0 | 최종 수정: 2026-06-23 | 관련 CR: CR-006

> 단계: 2. Architecture | 실행스펙 섹션 1에 포함
> 프로젝트 유형: **풀스택 (Spring Boot + React)** — 사용자 승인 완료(2026-06-19)

> **v1.0 → v2.0 변경(요지)**: ClickUp 기반(v0.3) → **Jira 방식 애자일**(v0.4) 전환은 **데이터 모델·화면(composite/features)의 변경**이며, **기술 스택 자체는 동일하다(재확인)**. BE/FE 프레임워크·DB·라이브러리·레포 구조·포트는 v1.0 그대로 유지하고, ds-ui 자체 제작 composite 목록과 frontend features 디렉토리만 v0.4 화면에 맞게 갱신했다.

## 조직 기술 제약 (0단계에서 확인)

> 아래 항목은 선택이 아닌 **전제 조건**이다. (`AI-SDLC_공통라이브러리_레퍼런스.md` 확인 결과)

- **공통 라이브러리**: `com.therecommerce:bp-common-lib:0.1.0` (GitHub Packages)
- **조직 표준 기술(BE 공통)**: Java 17, Spring Boot 3.x, **MyBatis**, Gradle(Kotlin DSL), 패키지 루트 `com.therecommerce.workmap`
- **사용 금지 기술**: **JPA / Hibernate 일절 사용 금지** (Auditing, Repository 포함)
- **참조 문서**: `AI-SDLC_공통라이브러리_레퍼런스.md`
- **에러 코드 범위**: 프로젝트 도메인 에러 코드는 **7700번대 이후** 사용

> **DB 결정(WorkMap 한정)**: bp-common-lib 레퍼런스의 공통 표준 DB는 MySQL이나, **본 프로젝트는 사용자 결정(2026-06-19)으로 PostgreSQL을 사용한다.** ORM은 조직 표준대로 MyBatis 유지(JPA 금지). bp-common-lib는 ORM 비의존(응답/예외/페이징/JWT/검색)이므로 PostgreSQL+MyBatis 조합과 충돌 없음.

## 기술 스택 (BE/인프라)

> FE 스택은 아래 별도 섹션. 이 표에는 BE/인프라만 기재.

| 영역 | 항목 | 선택 | 선택 이유 | 대안 검토 |
|------|------|------|----------|----------|
| 백엔드 | 언어 | Java 17 | 조직 표준 | (고정) |
| 백엔드 | 프레임워크 | Spring Boot 3.x | 조직 표준, bp-common-lib 호환 | (고정) |
| 백엔드 | 영속성 | MyBatis | 조직 표준(JPA 금지). 동적 필터 쿼리 적합 | JPA(금지) |
| DB | RDBMS | PostgreSQL 16.x | 사용자 결정(WorkMap 한정). JSONB·집계·부분 인덱스 | MySQL(공통 표준이나 미채택) |
| DB | 마이그레이션 | Flyway | 시드(상태/역할/워크플로/측정단위) + 버전 관리 | Liquibase |
| 인증 | 방식 | JWT + Refresh (bp-common-lib `JwtTokenProvider` 상속) | 라이브러리 제공, Stateless | Session |
| 공통 | 응답/예외/페이징/검색 | bp-common-lib | 직접 구현 금지 | (고정) |
| 이벤트 | Phase 1 | Spring ApplicationEvent | 인프로세스 알림/이력. 트랜잭션 보장 | Kafka(Phase 3+) |
| 빌드 | Gradle (Kotlin DSL) | 조직 표준 | | Maven |

### bp-common-lib 사용 매핑

| 영역 | 라이브러리 제공 | 적용 방식 |
|------|----------------|----------|
| 응답 포맷 | 예 | `ResponseDto`, `SuccessCode` 구현체(WorkMap 성공코드) |
| 에러 코드 | 예 | `ErrorCode` 구현체 — **7700번대** 도메인 에러 |
| 페이징 | 예 | `PageRequest`/`PageResponse`/`PagingRequestDto` 그대로 |
| 인증/인가 | 예 | `JwtTokenProvider`·`JwtFilter` 상속, `SecurityWhitelist` 구현체 |
| 검색/필터 | 예 | `SearchConditionRequest`/`SearchConditionUtil` — 업무 항목 통합 목록 필터(유형·상태·담당자·우선순위·라벨·스프린트·Epic·기한·막힘여부) 및 전체 텍스트 검색(기획서 §13.9 P1) |
| 로깅 | 예 | `RequestLoggingFilter`/`TraceIdFilter` 자동 등록 |
| 멱등 | 예 | `idempotency` (외부 수신 이벤트, Phase 4) |

> "예" 항목은 **직접 구현 금지**. DataSource/Mail/외부 연동 Config는 프로젝트에서 직접 정의.
> 검색·필터는 기획서 §13.9의 1차 핵심 사용성(안개 걷기·벌크 편집·받은함이 이 위에서 동작) — bp-common-lib `SearchConditionRequest` 기반으로 구현하며 별도 검색 DTO를 직접 만들지 않는다.

### ds-ui 사용 전략 (사용자 결정: "전체 그대로 + 부족분 자체")

- **그대로 사용**: base(Button/Input/Select/Table/Tabs/Badge/Dialog/Tooltip 등), layout(AdminShell/Sidebar/Header), composite(SearchInput/Pagination/DatePicker/DateRangePicker)
- **부족분(WorkMap에서 자체 제작)**: v0.4 Jira식 화면에 맞춘 업무관리 도메인 composite
  - `WorkItemCard` — 업무 항목 카드(구 TaskCard. Epic/Story/Task/Bug/Sub-task 단일 모델, 유형 표시 차등)
  - `KanbanColumn` / `KanbanBoard` — 운영형 칸반 보드(상태 컬럼, 카드 드래그앤드롭)
  - `BacklogRow` — 백로그 행(Epic 펼침 트리, 인라인 편집)
  - `SprintHeader` — 스프린트 헤더(이름·기간·항목수·상태별 카운트·추정치 합·시작/완료 액션)
  - `StatusBadge` — 워크플로 상태 배지(워크플로별 상태색)
  - `TypeBadge` — 업무 유형 배지(Epic/Story/Task/Bug/Sub-task)
  - `MeasureBar` — 목표·실적 측정 바(측정단위 + 목표값/현재값 + 진행률, §8.5)
  - `SplitView` — 목록 분할뷰(좌 리스트 + 우 상세 패널, §9.5)
  - `CreateModal` — 업무 만들기 모달(공통+극소수 필드, 유형 무관 동일 모달, §9.4)
  - 자체 제작분도 ds-ui의 base 컴포넌트 + Tailwind 토큰으로 조립한다(일관성).

- **기준 색감(목업 톤 유지, 사용자 승인 2026-06-23)**: 현 frontend 목업의 색감을 기준 팔레트로 유지한다. 실측 사용 비율 = **slate(중립 회색) 압도적 베이스** + 신호색 절제(red=막힘/삭제/지연, blue=주요 액션/링크, amber=경고/보류, green=완료, violet=Epic). 즉 "중립 회색 레이아웃 + 신호에만 색"이 이미 CLAUDE.md UI 규칙(색 절제)과 일치 — 이 톤을 구현에서 이어간다. 신호 의미↔색 매핑은 위 규칙대로 고정.
  - 2개 이상 프로젝트에서 재사용될 것으로 판단되면 ds-ui 기여 후보로 기록(CLAUDE.md).
- ds-ui 설치: `pnpm add @therecommerce/ds-ui@github:therecommerce/design-system#main`
- main.tsx: `import '@therecommerce/ds-ui/dist/style.css'` (+ 사내툴 테마 확정 시 테마 css)

## 측정 추상화 (Phase 1 포함)

> 목표·실적 측정 추상화(기획서 §8.5/8.6)는 **Phase 1에 포함**한다.

- `measure_unit`(측정 단위 마스터): 관리자 관리 테이블, 시스템 기본 시드 제공(건수/금액/%/시간/완료여부 등). 코드 enum 하드코딩 금지 — Flyway 시드 + 관리자 행 추가.
- `work_item`은 `(measure_unit_id, target_value, current_value)`로 목표·실적 표현, 진행률 자동 계산(정성은 상태 기반).
- 개발(정성)·운영(정량) 업무가 **한 모델**(work_item + 측정 추상화)로 묶임 → 별도 처리량 모델 불필요(§15.1-11).
- 마스터 데이터 원리는 `field_scheme`(필드 스킴)·`workflow`(상태·전이)·`issue_type`에도 동일 적용(관리자 설정, §13.5).

## 인증/보안 설계

- JWT Access + Refresh (bp-common-lib `JwtTokenProvider` 상속, 클레임에 userId/role/deptId 포함)
- `SecurityWhitelist` 구현체: `/api/v1/auth/login`, `/actuator/health` 등 공개 경로
- 권한: 역할(Owner/Admin/Manager/Member/Viewer)을 메서드/엔드포인트 단위로 검사(POL-004)
- 프로젝트 가시성(기획서 §13.5 P1): 프로젝트의 공개/비공개 + 멤버십 + 사용자 권한으로 업무 항목 조회 필터

## 인프라/배포 개요

- Phase 1: 단일 서버(WAR/Jar) + PostgreSQL. 운영 배포는 프로젝트 루트 `deploy.sh` 표준(도입 시).
- 포트 레지스트리(전역 규칙): BE **8186**, FE는 BE-5000 = **3186**. (전역 포트 테이블 등록 완료)
- CI/CD: GitHub Actions (조직 표준), GitHub Packages 인증(read:packages 토큰).
