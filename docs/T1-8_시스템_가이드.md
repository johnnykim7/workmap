# WorkMap 시스템 가이드 (비개발자용)

> 설계 버전: 2.0 | 최종 수정: 2026-06-23 | 관련 CR: CR-006

> 단계: 1. Requirements | 이해관계자 리뷰 및 피드백 수집용
>
> 기술 용어 없이, 대표·관리자·실무자가 "이 시스템이 무엇을 하는지"를 이해하고
> "우리 일하는 방식과 맞는지" 확인할 수 있도록 쓴 문서입니다.

---

## 1. WorkMap이 뭔가요?

> **WorkMap(업무지도)은 흩어져 있는 우리 회사의 모든 업무를 한곳에 모아, 무엇이 막혀 있고 무엇이 늦어지고 있는지를 빨리 발견하게 해주는 내부 업무 시스템입니다.**

지금 우리 일은 메신저·이메일·구두 지시·엑셀 여기저기에 흩어져 있습니다. 그래서 누가 무엇을 하는지, 어디서 멈춰 있는지, 무엇이 늦었는지가 한눈에 안 보입니다. 작은 조직일수록 "무엇이 막혀 있는지(blocked)"가 안 보이는 게 치명적입니다.

WorkMap은 이 모든 일을 하나의 시스템에 등록하게 합니다. 그리고 그 **하나의 업무 데이터**를 백로그·보드·목록·회사 홈 같은 여러 화면으로 비춰 보여 줍니다.

일하는 방식은 IT 팀이 널리 쓰는 **애자일(Jira) 방식**을 기본으로 하되, 우리 회사의 물류 현장(입고·출고·반품·운영) 특성에 맞게 다듬었습니다. 즉 "개발 일"과 "현장 운영 일"을 같은 도구에서 다룹니다.

**판매용 제품이 아닙니다.** 우리 내부에서 쓰려고 만드는 운영 도구입니다.

---

## 2. 일이 어떻게 흘러가나요?

WorkMap에서 일은 다음 순서로 흘러갑니다.

```
[① 업무를 등록한다]
   큰 일은 Epic, 사용자 가치는 Story,
   실제 작업은 Task, 오류는 Bug, 세부 작업은 Sub-task로
        ↓
[② 백로그에 쌓는다]
   "언젠가 할 일" 후보를 한곳에 모아 둠
        ↓
[③ 이번에 할 일을 스프린트로 끌어올린다]
   "이번 1~2주에 할 것"만 골라서 묶음(=스프린트)
        ↓
[④ 보드에서 상태를 옮기며 실행한다]
   카드를 끌어다 옮기며 진행
        ↓
[⑤ 막힘·지연을 시스템이 자동으로 잡아 준다]
   막힌 일·늦은 일·담당자 없는 일을 알아서 모아 표시
        ↓
[⑥ 회사 홈에서 전체를 한눈에 본다]
   대표·관리자가 별도 보고 없이 현황 확인
```

### 업무의 다섯 가지 종류

모든 일은 아래 다섯 종류 중 하나로 등록합니다. 이슈·장애·요청도 전부 이 안에 들어갑니다(따로 다른 시스템을 쓰지 않습니다).

| 종류 | 뜻 | 예시 |
|------|----|------|
| Epic(에픽) | 큰 기능·산출물 단위. 여러 작은 일로 쪼개지는 큰 덩어리 | "입고 관리", "출고 관리" |
| Story(스토리) | 사용자·현장 관점의 가치 | "작업자가 바코드로 입고 상품을 조회한다" |
| Task(작업) | 가치를 만드는 실무 작업 | "상품 조회 화면 개발" |
| Bug(버그) | 오류·결함 | "입고 확정 시 재고가 두 번 늘어남" |
| Sub-task(하위 작업) | 더 잘게 쪼갠 세부 실행 | "수량 입력 칸 만들기" |

> **순서를 강요하지 않습니다.** "Story를 먼저 만들어야 Task를 달 수 있다" 같은 규칙은 없습니다. 다섯 종류는 항상 다 쓸 수 있고, 어느 것부터 등록할지는 사람이 정합니다. (도구가 현장을 막으면 사람들이 그 도구를 안 쓰게 되기 때문입니다.)

### 백로그와 스프린트의 차이

- **백로그** = 아직 "이번 주기에 한다"고 정하지 않은 일 후보를 모아 둔 곳
- **스프린트** = "이번 1~2주에 하기로" 골라 담은 일 묶음

둘은 같은 업무이고, 차이는 "실행했느냐"가 아니라 "언제 할지 정했느냐"입니다. 한 화면(백로그 화면) 안에서 일을 백로그↔스프린트로 끌어 옮기며 계획합니다.

## 3. 업무 상태가 어떻게 바뀌나요?

업무는 진행되면서 상태가 바뀝니다. 업무 종류·프로젝트에 따라 상태 흐름이 조금씩 다릅니다.

### 개발 일의 흐름

```
  할 일
    │  착수
    ▼
  진행 중
    │  검토 요청
    ▼
  검토 중
    │  통과
    ▼
   완료 ───── 끝난 날짜가 자동으로 기록됨
```

### 현장 운영 일의 흐름

```
  접수 → 확인 중 → 처리 중 → 현장확인 → 완료
                                      (또는 보류)
```

### 개발 완료와 현장 반영을 구분하는 흐름 (WorkMap 특화)

개발이 끝났다고 일이 끝난 게 아닙니다. 현장에 실제로 적용되어야 진짜 완료입니다.

```
  할 일 → 진행 중 → 개발완료 → 현장검증중 → 운영반영완료
```

### 어느 흐름이든 공통

```
  진행 중 ── 막히면 → "막힘(BLOCKED)" (막힌 이유를 꼭 적어야 함)
```

**꼭 지켜지는 규칙 (시스템이 강제합니다)**

- 모든 업무는 반드시 **하나의 프로젝트**에 속해야 등록됩니다.
- 업무를 **"막힘"으로 바꾸면 막힌 이유를 반드시 적어야** 합니다. 이유 없이는 막힘으로 바꿀 수 없습니다.
- 업무를 **"완료"로 바꾸면 완료한 날짜가 자동**으로 들어갑니다.
- 마감일이 지났는데 끝나지 않은 일은 **자동으로 "지연"**으로 잡힙니다.
- 업무를 지워도 데이터는 보존됩니다(완전히 사라지지 않음). 실수로 지워도 안전합니다.
- 상태는 정해진 순서(허용된 다음 상태)로만 바뀝니다. 아무 상태로나 건너뛸 수 없습니다.

> 담당자는 **권장이지 필수가 아닙니다.** 등록을 가볍게 하기 위해 담당자 없이도 일단 등록할 수 있습니다. 단, 담당자 없는 일은 회사 홈에서 따로 모아 강조해 보여 줘서 빠뜨리지 않게 합니다. (※ 이전 버전에서는 담당자가 필수였으나, "등록 마찰을 줄이자"는 결정으로 권장으로 바뀌었습니다.)

## 4. 화면별로 무엇을 하나요?

### 회사 홈 (막힘 중심 대시보드)

대표·관리자가 가장 먼저 보는 화면입니다. 작은 조직은 "전체 진행률 몇 %"보다 **"무엇이 막혀 있나"**가 더 중요합니다. 그래서 다음을 화면 위쪽에 크게 보여 줍니다.

- 막힌 업무 (그리고 왜 막혔는지)
- 마감이 지난 지연 업무
- 담당자가 없는 업무
- 검토 단계에서 멈춰 정체된 업무
- 심각한 Bug
- 현장검증을 기다리는 업무 / 운영 반영을 기다리는 업무

대표가 별도로 보고를 요청하지 않아도, 이 화면에 들어오면 현황이 보입니다.

### 백로그 (계획하는 화면)

"앞으로 할 일"을 쌓아 두고, 이번에 할 것을 골라 스프린트로 올리는 화면입니다.

- 현재 진행 중인 스프린트 + 예정된 스프린트 여러 개 + 백로그가 한 화면에 줄지어 보입니다.
- 일을 끌어다 스프린트↔백로그로 옮기고, 순서를 바꿉니다.
- 스프린트를 **시작**하면 이번에 할 일과 기간이 확정됩니다.
- 스프린트를 **완료**하면 못 끝낸 일은 다음 스프린트나 백로그로 넘길 수 있습니다.

### 보드 (실행하는 화면)

이번 스프린트의 일을 카드로 펼쳐 놓고, 카드를 끌어다 옮기며 상태를 바꾸는 화면입니다.

- 개발 일: 백로그 → 선택됨 → 진행 중 → 완료
- 운영 일: 접수 → 확인 중 → 처리 중 → 현장확인 → 완료 / 보류

### 목록 (전체를 표로 보는 화면)

모든 업무를 표로 보고, 검색·필터·정렬하는 화면입니다.

- 보고 싶은 조건으로 거를 수 있습니다 (종류·상태·담당자·우선순위·마감·막힘 여부 등).
- 자주 쓰는 빠른 필터: "내 일 / 막힌 것 / 담당자 없는 것".
- 화면을 둘로 나눠 왼쪽엔 목록, 오른쪽엔 선택한 업무의 상세를 동시에 볼 수 있습니다(페이지 이동 없이 연달아 처리).
- 여러 업무를 한꺼번에 골라 상태·담당자·스프린트를 **일괄 변경**할 수 있습니다(아래 6번 "안개 걷기"에 유용).

### 업무 상세 (종류별로 다르게 보임)

한 업무를 열면, 그 종류에 맞는 내용이 보입니다.

- Epic: 하위 업무 묶음 + 전체 진행률
- Story: 인수조건(이걸 할 수 있으면 끝) + 하위 작업
- Task: 작업 체크리스트 + 들인 시간
- Bug: 어떻게 재현되나 / 기대 vs 실제 / 환경 / 심각도
- Sub-task: 부모 업무 링크 + 간단 정보
- 모든 종류 공통: 연결된 다른 업무 · 관련 문서 · 첨부파일 · 댓글 · 변경 이력

> "하위 작업"과 "연결된 업무"는 다릅니다. 하위 작업은 부모-자식 관계(쪼갠 것)이고, 연결된 업무는 "이게 저걸 막고 있다 / 관련 있다" 같은 가로 연결입니다.

### 관리자 설정 (코드 수정 없이 회사에 맞게 조정)

관리자가 회사 상황에 맞게 직접 조정하는 화면입니다. 새 항목이 필요해도 개발자에게 요청할 필요 없이 여기서 추가합니다.

- **측정 단위**: 목표·실적을 무엇으로 잴지(건수·금액·%·시간·완료여부 등)
- **표시 필드**: 업무 종류별로 어떤 칸을 보여 줄지 켜고 끄기
- **워크플로**: 업무 상태와 그 흐름(어디서 어디로 갈 수 있나)
- **업무 유형**: 기본 5종 외에 운영요청·승인요청·현장검증 같은 종류 추가
- **양식**: 외부/현장에서 요청을 받을 수 있는 제출 양식 만들기

> 회사 처음 쓸 때 손볼 필요가 없도록, 자주 쓰는 항목은 **미리 들어 있습니다**(기본 제공). 그대로 써도 되고, 필요할 때 추가하면 됩니다.

## 5. WorkMap만의 특징

### 하나의 업무 데이터, 여러 관점

이게 가장 중요한 컨셉입니다. 목록·보드·백로그·타임라인·이슈 화면은 **서로 다른 데이터가 아니라 같은 업무 데이터를 다르게 비춘 것**입니다. 한 화면에서 바꾸면 다른 화면에도 즉시 반영됩니다. 따로따로 관리하다 어긋날 일이 없습니다.

### 목표와 실적을 한 모델로 측정

개발 일은 "완료/미완료"로, 운영 일은 "50건 중 43건"처럼 숫자로 잽니다. 단위가 다릅니다. WorkMap은 이걸 따로 나누지 않고 **하나의 방식으로 통일**합니다.

| 업무 | 단위 | 목표 | 현재 | 진행 |
|------|------|------|------|------|
| 반품 검수 | 건수 | 50건 | 43건 | 86% |
| 외주비 절감 | 금액 | 300만 원 | 120만 원 | 40% |
| API 개발 | 완료여부 | 완료 | 진행 중 | 상태 기반 |

덕분에 개발 일과 운영 일, 회사 목표까지 같은 화면에서 비교할 수 있습니다. (이건 Jira에는 기본으로 없는 WorkMap의 차별점입니다.)

### 운영 ↔ 개발 개선 루프

현장 운영 중에 발견한 문제를 곧바로 **개발 백로그로 넘길 수 있습니다**(원본 연결 유지). "현장에서 막힌 것 → 개발이 고침 → 다시 현장 검증" 순환이 끊기지 않게 이어 줍니다. 이 연결이 WorkMap의 핵심 가치입니다.

### 막힘 중심 관리

진행률 위주의 화려한 대시보드 대신, **"지금 무엇이 멈춰 있나"**를 가장 크게 보여 줍니다. 작은 조직에 맞는 운영 방식입니다.

## 6. 처음엔 어떻게 쓰나요? — "안개 걷기"

WorkMap의 **1차 목적은 새 일을 관리하는 게 아니라, "그동안 한 일의 현황을 다시 정리하는 것"**입니다. AI로 빨리 달려왔지만 뚜껑을 열어 보니 무엇이 어디까지 됐는지 안 보이는 "안개" 상태를 걷어 내는 게 첫 사용 목적입니다.

1. **다 끄집어내기**: 3월 이후 만든 기능(반품구조대·WMS 등)을 전부 업무로 등록합니다.
2. **냉정하게 다시 분류**: 각 일을 "완료/구현됐지만 미검증/운영테스트 필요/수정 필요/재설계 필요/후순위"로 솔직하게 나눕니다.
3. **완료 기준 다시 세우기**: "개발 완료 = 업무 완료"가 아닙니다. 현장에서 검증돼야 진짜 완료입니다.
4. **1~2주 안정화 계획**: 이번에 할 것만 고르고, **"이번엔 안 할 것"도 명시**해 일이 무한정 늘어나는 걸 막습니다.
5. **운영검증 → 다음 계획**: 검증 결과에서 나온 다음 할 일을 다시 백로그로 넣습니다.

> 첫 적용 대상은 **반품구조대 1차 운영 안정화**입니다.

## 7. 자주 묻는 질문 (FAQ)

**Q. 업무를 등록할 때 담당자를 꼭 정해야 하나요?**
→ 아니요. 담당자 없이도 일단 등록할 수 있습니다. 나중에 정하면 됩니다. 다만 담당자 없는 일은 회사 홈에서 따로 모아 보여 줘서 잊지 않게 합니다.

**Q. Story를 먼저 만들어야 Task를 만들 수 있나요?**
→ 아니요. 순서는 자유입니다. Task만 먼저 만들어도 되고, Bug부터 등록해도 됩니다. 도구가 순서를 강요하지 않습니다.

**Q. 이슈·리스크·버그는 따로 등록하는 시스템이 있나요?**
→ 아니요. 전부 "업무"의 한 종류이거나 업무에 붙은 신호입니다. 버그는 업무 종류 'Bug'로, 막힘·지연은 업무 상태로 표시됩니다. 별도 시스템을 쓰지 않습니다.

**Q. 회의에서 나온 할 일은 어디에 적나요?**
→ 메신저에만 남기지 말고 WorkMap에 업무로 등록합니다. 담당자·마감일을 정하면 자동으로 추적됩니다.

**Q. 대표가 현황을 보려면 보고서를 요청해야 하나요?**
→ 아니요. 회사 홈에 들어가면 막힘·지연·담당자 없음 현황이 자동으로 보입니다.

**Q. 개발이 끝나면 그 일은 완료인가요?**
→ 아닙니다. 개발 완료와 현장 운영 반영을 따로 추적합니다. 현장에 실제로 적용·검증돼야 진짜 완료입니다.

**Q. 마감일을 안 적으면 어떻게 되나요?**
→ 등록은 됩니다. 다만 마감일이 없으면 지연 관리가 안 되므로, 마감 없는 일이 많지 않게 하는 게 좋습니다.

**Q. 개발 일과 운영 일을 같은 도구로 관리할 수 있나요?**
→ 네. 개발 일은 백로그·스프린트·보드로, 운영 일은 칸반과 처리량 뷰로 다룹니다. 둘 다 같은 시스템 안에서 함께 봅니다.

**Q. 비공개로 두고 싶은 프로젝트가 있어요.**
→ 프로젝트를 비공개로 설정하면 그 프로젝트 멤버만 보고 검색할 수 있습니다. 회사 홈 집계에도 볼 권한이 있는 것만 반영됩니다.

## 8. 1차 개발 범위 (먼저 만드는 것)

이번 1차에서 우선 만드는 것:

- 로그인 / 사용자·멤버 관리 / 프로젝트 공개·비공개 설정
- 업무 등록·수정·삭제 / 다섯 종류 + 계층 / 담당자·상태·마감
- 백로그 / 스프린트 시작·완료 / 보드(상태 옮기기)
- 목표·실적 측정 / 검색·필터·빠른 필터 / 여러 업무 일괄 변경 / 종류 전환
- 운영 칸반 / 처리량 뷰 / 현장 이슈 → 개발 백로그 전환
- 회사 홈(막힘·지연·미배정 자동 집계) / 프로젝트 보고서
- 관리자 설정(측정 단위·표시 필드·워크플로) / 인앱 알림

다음 단계로 미루는 것: 번다운 차트·타임라인·캘린더·현장검증 기록 고도화·양식 빌더·업무 간 링크 고도화·저장 필터, 그리고 채널 소통(슬랙형 채널)·외부 알림(Slack/메일)·AI 기능 등.
